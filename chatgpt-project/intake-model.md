# Intake Model

The intake model defines how demand becomes reviewable portfolio work.

## Minimum intake fields

| Field | Why it matters |
|---|---|
| Request title | Provides a stable reference |
| Sponsor | Prevents orphan demand |
| Problem statement | Separates pain from proposed solution |
| Desired outcome | Clarifies value expectation |
| Initiative type | Routes work correctly |
| Portfolio lane | Enables ownership and reporting |
| Required timing | Reveals urgency and deadlines |
| Funding status | Separates committed work from asks |
| Known dependencies | Exposes sequencing risk |
| Risk or compliance driver | Flags special review needs |
| Current evidence | Shows whether review is possible |
| Decision needed | Forces clarity on why governance is involved |

## Intake states

New, incomplete, needs sponsor, discovery, business case needed, charter needed, ready for scoring, rerouted, deferred, and rejected.

## Output

Produce entry channels, minimum fields, intake states, review cadence, decision points, rejection and deferral reasons, handoff rules, and what not to intake.

## Guardrail

Intake acceptance is not project approval. Make that distinction explicit.
